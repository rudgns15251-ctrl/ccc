| 영역 | 상태 |

## 2. 추천 순서

### 단계 A — 프리뷰 플레이 검증 (지금 가능, 1~2주)
- `CAP_Preview.exe`를 사용자 본인 + 1~3명이 플레이합니다(약 15분). README의 5가지 질문으로 메모합니다.
- 결과로 판단할 것: 추론의 재미가 있는가, 지연 판정과 방송이 긴장감을 주는가, UI가 이해되는가.
- 이 결과가 단계 C(정식 Case 설계)의 기준이 됩니다.

### 단계 B — 이야기 방향과 정식 Case 1 확정 **[결정 필요]**
1. **이야기 방향**(설계 평가 보고서 6장): 방향 1(인수인계받은 연구원) / 방향 2(방송을 맡은 야간 통제원) / 방향 3(사고 기록 감사관). 제 추천은 방향 1 + 방향 2의 방송 책임입니다.
2. **플레이어 신분과 동기, 전임자의 존재 여부.**
3. **첫 정식 개체:** 외형(이미지 또는 설명), 기본 성질, 올바른 격리 조건의 핵심 원리. T04를 정식으로 승격할지, 새 개체로 할지도 여기에 포함됩니다.
4. **본편 틀과 출시 범위:** **[APPROVED 2026-10-16] 정식 9개 Case + 기록 없는 숨겨진 개체 1을 모두 출시**(약 90~120분 목표). 앞서 정했던 "1차 4~5 Case·60분"은 이 결정으로 대체됐습니다.
   - **[APPROVED] 이야기: C. 결합안**(연구원 자리 승계 + 야간 방송 책임).
   - [판단] 범위가 커졌으므로 단계 D는 "Case 1~3 → 중간 프리뷰 빌드 → Case 4~9 → 숨겨진 개체·엔딩" 순서로 나누어 매 묶음마다 플레이 검증을 거치는 것을 권장합니다.
5. **Case 1:** **[APPROVED] 시선 반응 개체**(감시 조명·카메라 표시등에 반응, 적외선 감시실이 정답 방향). 외형과 세부 문구는 DRAFT입니다.

### 단계 C — 정식 Case 1 수직 슬라이스 (B 결정 후)
- Profile, CCTV, 실험, 격리 후보, 지연 결과, 사고, 방송, 보고서, Research를 정식 문구로 작성합니다(QA에서 찾은 추론 설계 원칙 적용).
- 출시 UI를 **F5 본편 진입점으로 이전**합니다(**[결정 필요]**: 기본 F5 변경 승인).
- 정식 Case에 맞는 이미지 제작 방식을 결정합니다(직접 / 외주. 에셋 계획서 3장).

### 단계 D — 본편 Campaign 골격
- 정식 Case 4~5개(1차 출시 기준), 강제 사건 1~2개, Story Record 12개 배치, 엔딩 1~2종 **[결정 필요: 결말 방향]**.
- 저장 슬롯과 새 게임 흐름, 튜토리얼(첫 근무 안내).

### 단계 E — 출시 준비
- 키 아트·스토어 캡슐 외주(에셋 계획서 4장), 스토어 페이지 문구, 트레일러용 캡처.
- 해상도·창 모드·키 설정, 접근성(글자 크기는 완료), 한국어·영어 지원 범위 결정.
- 외부 플레이 테스트(5~10명), 버그 수정, 최종 라이선스 점검.

## 4. 위험
- **콘텐츠 없이 UI만 다듬는 위험**: 지금이 그 지점입니다. 다음 단계부터는 콘텐츠 결정이 없으면 진척이 제한됩니다.
- **범위 과대**: 9+1 Case, 90~120분은 1인 또는 소규모 개발에 큰 목표입니다. 1차 출시를 작게 잡고 업데이트로 확장하는 편이 현실적입니다.
- **사람 검증 부재**: 자동 검사 통과는 재미와 이해도를 보장하지 않습니다.
